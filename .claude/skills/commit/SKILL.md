# Commit

작업한 변경사항을 저장소 컨벤션에 맞는 커밋으로 만든다.

커밋은 나중에 히스토리를 읽는 사람(대개 미래의 본인)을 위한 기록이다. 그래서
"무엇을 바꿨는지"보다 "왜 바꿨는지"가 남아야 하고, 한 커밋에는 하나의 작업만
들어가야 되돌리거나 리뷰하기 쉽다. 아래 절차는 그 두 가지를 지키기 위한 것이다.

## 1. 변경사항 확인

먼저 무엇이 바뀌었는지 실제로 읽는다. diff를 보지 않고 쓴 커밋 메시지는
추측이 되기 쉽다.

```bash
git status
git diff              # 스테이징 안 된 변경
git diff --staged     # 이미 스테이징된 변경
```

diff가 길면 `git diff --stat`으로 전체 윤곽을 먼저 잡고, 핵심 파일만 자세히 본다.

## 2. 관련 파일만 스테이징

이번 작업과 관련된 파일만 고른다. `git add .` 나 `git add -A`는 무관한 변경이
섞여 들어가므로 쓰지 않고, 경로를 명시해서 추가한다.

```bash
git add lib/todo-utils.ts components/todo-sort.tsx
```

판단 기준:

- 이번 작업 목적에 직접 기여하는 파일 → 포함
- 우연히 같이 열려 있던 파일, 실험하다 만 코드, 임시 로그 → 제외
- `.env`, 로컬 설정, 빌드 산출물, 자격증명처럼 커밋되면 안 되는 파일 → 제외하고
  사용자에게 알린다

성격이 다른 변경이 섞여 있으면(예: 기능 추가 + 무관한 리팩터링) 한 번에 묶지 말고
커밋을 나누거나, 어떻게 나눌지 사용자에게 물어본다.

## 3. 커밋 메시지 작성

메시지를 쓰기 전에 이 저장소의 최근 커밋 형식을 확인한다. 컨벤션은 저장소마다
미묘하게 다르고, 히스토리가 가장 정확한 기준이다.

```bash
git log --format='%s%n%b---' -10
```

이 저장소의 형식은 다음과 같다:

```
<type>: <한국어 요약>

- 변경 내용 1
- 변경 내용 2
```

- **type**: `feat`, `fix`, `refactor`, `docs`, `test`, `chore` 중 실제 변경 성격에 맞는 것
- **요약**: 한국어 명사형 마무리(`~추가`, `~수정`, `~제거`), 50자 이내, 마침표 없음
- **본문**: 변경이 여러 갈래이거나 이유 설명이 필요할 때만 쓴다. 한 줄짜리 단순
  변경에 억지로 본문을 붙이지 않는다.
- scope는 필요할 때만 쓴다(`refactor(course):`처럼). 대부분의 커밋은 생략한다.

예시:

```
feat: 카테고리별 Todo 필터 추가

- CategoryFilter 타입과 CATEGORY_FILTERS 옵션 추가
- 카테고리 필터 UI(TodoCategoryFilter, 전체/업무/개인/쇼핑) 추가
- 목록 파생 상태에 카테고리 필터 합성('전체'는 필터 해제)
```

```
docs: README에 개발 서버 실행 명령어 추가
```

메시지에는 diff를 그대로 옮기지 말고, 그 변경이 사용자/코드에 어떤 차이를
만드는지 쓴다. "todo-utils.ts 수정"이 아니라 "마감일순 정렬 추가"다.

## 4. 커밋하고 결과 확인

여러 줄 메시지는 heredoc으로 전달해 줄바꿈을 유지한다.

```bash
git commit -m "$(cat <<'EOF'
feat: 카테고리별 Todo 필터 추가

- CategoryFilter 타입과 CATEGORY_FILTERS 옵션 추가
- 카테고리 필터 UI 추가
EOF
)"
```

커밋 후 실제로 무엇이 들어갔는지 확인한다. pre-commit 훅(bun 기반 lint/test 등)이
파일을 고치거나 커밋을 막을 수 있어서, 성공했다고 가정하지 않고 눈으로 본다.

```bash
git status
git log -1 --stat
```

훅이 파일을 수정했다면 그 결과를 확인하고 필요하면 다시 스테이징해 커밋한다.
커밋이 실패했다면 원인(훅 실패, lint 오류 등)을 사용자에게 그대로 전한다.

마지막으로 커밋한 내용과, 스테이징하지 않고 남겨둔 변경이 있다면 무엇인지
사용자에게 한 줄로 보고한다.

## 하지 않을 것

- `git push` — 사용자가 명시적으로 요청할 때만 한다
- `git commit --amend`, `git rebase`, `git reset --hard` — 이미 있는 히스토리를
  바꾸는 명령은 요청받았을 때만 쓴다
- `git add .` / `git add -A` — 의도하지 않은 파일이 섞인다
- `--no-verify` — 훅을 우회하지 않는다
